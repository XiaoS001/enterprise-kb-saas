## 一、启动

### 本地

```bash
python -m venv venv
venv\Scripts\activate           # Windows
pip install -r requirements.txt
python app.py                   # → http://127.0.0.1:5001
```

### Docker

```bash
docker compose up -d            # 推荐（命名卷，权限无需操心）
docker compose logs -f rmb01
docker compose down             # 保留数据卷
docker compose down -v          # 🔴 连数据一起删
```

### 首次部署必做

1. **配 `RMB01_SECRET_KEY`** —— 否则每次重启 session 全失效
   （`GET /healthz` 返回 `secret_key_ephemeral: true` 时说明没配）
2. **配 `RMB01_PASSWORD_SALT`**
3. **决定要不要配 `DEEPSEEK_API_KEY`** —— 不配则走降级路径（不扣额度）
4. 初始化平台管理员：

```python
from app import app
from models import init_platform_admin
with app.app_context():
    init_platform_admin('admin', '你的强密码')
```

| 字段 | 该看什么 |

## 三、常见故障

### 3.1 `database is locked`

**症状**：并发请求时报 `sqlite3.OperationalError: database is locked`

**原因**：SQLite 同一时刻只允许一个写者。

**排查**：

```bash
# 确认 WAL 开了
sqlite3 data/rmb01.db "PRAGMA journal_mode;"      # 应输出 wal
sqlite3 data/rmb01.db "PRAGMA busy_timeout;"      # 应 >= 5000
```

**修复**：

| 情况 | 做法 |
|---|---|
| 没开 WAL | 检查 `billing.apply_sqlite_pragmas` 是否挂在 `connect` 事件上 |
| 开了还锁 | 🔴 检查 worker 数 —— 多 worker 必然锁冲突，见下条 |
| 长期高并发 | 换 PostgreSQL |

### 3.2 多 worker 启动被拒

**症状**：容器起不来，日志里有「SQLite 并发写冲突」

这是 `entrypoint.sh` 的**防呆**，不是 bug。

```bash
# 确认 worker 数
docker exec rmb01 env | grep GUNICORN_WORKERS    # 应为 1
```

**要横向扩展**：

1. 换 PostgreSQL：`RMB01_DATABASE_URL=postgresql+psycopg://...`
2. 再设 `GUNICORN_WORKERS=N`
3. 若明知风险还要强开：`RMB01_ALLOW_MULTI_WORKER=true`（**不推荐**）

### 3.3 容器启动报「数据目录不可写」

```
❌ 数据目录不可写：/app/data（当前用户 appuser）
```

容器以 **非 root**（uid 1001）运行，挂载的宿主目录需要可写权限。

```bash
# 方案 A：用命名卷（compose 默认，推荐）
docker compose up -d

# 方案 B：给宿主目录放权
mkdir -p ./data && chmod 777 ./data
```

### 3.4 `/healthz` 一直不 ready

```bash
docker logs rmb01 --tail 50
```

常见原因：

| 日志 | 原因 |
|---|---|
| `ModuleNotFoundError` | 镜像构建时依赖没装（检查 `requirements.txt`） |
| `Address already in use` | 5001 被占用 |
| `Permission denied: ./entrypoint.sh` | 🔴 可执行位丢了（Windows 上 git 不保存），Dockerfile 里 `chmod +x` 修复 |

### 3.5 问答一直返回「知识库中没有相关内容」

**排查顺序**：

1. **库里真有文档吗？**
   ```bash
   curl -b cookie.txt http://127.0.0.1:5001/api/kbs/1/documents
   ```
2. **问题和文档有词面重叠吗？** BM25 是词面检索，同义词不认
   （「连接池」不会匹配「连接缓存」）
3. **相关性阈值是不是太高了？**
   ```bash
   RMB01_BM25_RELATIVE_THRESHOLD=0.1 python app.py     # 调低试
   ```
4. **是不是单文档库？** 已修，但确认下 `kb_search.py` 里那段特判还在

### 3.6 额度扣得比预期快

**先看是不是降级**：

```bash
curl -b cookie.txt http://127.0.0.1:5001/api/org/billing
```

```json
"usage": { "total_queries": 400, "billable_queries": 350, "degraded_queries": 50 }
```

`degraded_queries` 高 = 大量请求没调成模型（该查 key 或网络）。

**核账实相符**：

```sql
-- 应等于 subscription.quota_used
SELECT COUNT(*) FROM usage WHERE tenant_id = 1 AND degraded = 0;
SELECT quota_used FROM subscription WHERE tenant_id = 1;
```

两条不一致就是 bug，请提 issue。

### 3.7 引用校验拦住了正常答案

**症状**：`invalid_citations` 非空，但答案看起来没问题。

**原因**：答案里的 `[doc:N]` 的 N 不在召回结果里。可能：

| 情况 | 说明 |
|---|---|
| 模型自己编了 doc_id | 正常拦截，符合预期 |
| 引用了**上一轮**的 doc_id | 多轮对话里没重置证据集 |
| 引用格式不是 `[doc:N]` | 校验器只认 `[12]`/`【12】`/`[Q12]`/`[doc:N]` 几种 |

**临时放宽**（不推荐）：改 `skills/check_citation.py` 的 `_CITATION_PATTERN`。

## 四、备份与恢复

### 备份

```bash
# SQLite 用 .backup 而不是 cp —— 后者在 WAL 模式下可能拷到不一致状态
sqlite3 data/rmb01.db ".backup /backup/rmb01-$(date +%F).db"

# 容器内
docker exec rmb01 sqlite3 /app/data/rmb01.db ".backup /app/data/backup.db"
docker cp rmb01:/app/data/backup.db ./rmb01-$(date +%F).db
```

### 恢复

```bash
docker compose down
cp rmb01-2026-10-17.db ./data/rmb01.db
docker compose up -d
```

⚠️ **没有自动备份机制** —— `RMB01_BACKUP_DIR` 配置项存在但没接定时任务。

## 五、日志

全部输出到 **stdout**（12-factor），不加文件 handler。

```bash
docker compose logs -f rmb01
docker compose logs rmb01 | grep user_login          # 登录审计
docker compose logs rmb01 | grep record_usage_failed # 计量异常
```

关键日志事件：

| 事件名 | 含义 |
|---|---|
| `user_login` | 登录成功（含 username/role） |
| `permission_denied` | 权限不足（排查越权） |
| `record_usage_failed` | 🔴 计量失败（**问答仍会成功**，但账目可能漏） |
| `ask_via_agent_failed` | agent 调用异常，走了降级 |
| `sqlite_pragmas_failed` | ⚠️ PRAGMA 没设上，并发会出问题 |

## 七、监控现状

### ✅ 有的

| 手段 | 说明 |
|---|---|
| `/healthz` | Docker HEALTHCHECK 用它，30s 一次 |
| stdout 日志 | 结构化 event 名，可被日志系统采集 |
| `/api/org/billing` | 业务层用量（计费/降级/额度） |
| `/api/platform/usage-ranking` | 跨租户用量排行 |

### ❌ 没有的（如实说明）

| 项 | 状态 |
|---|---|
| **`/metrics` 端点** | 🔴 **未实现** —— 所以 `docker-compose.yml` 里**没有** Prometheus/Grafana。摆着采不到业务指标是假把式 |
| 分布式追踪 | 无 |
| 告警规则 | 无（套餐表里写了短信/webhook，没做） |
| 性能指标（QPS/延迟） | 无 |

**要做可观测性的正确顺序**：先在 `app.py` 加 `/metrics`
（业务指标：问答次数、降级率、额度消耗、检索命中率），
再接 Prometheus/Grafana。

## 八、安全清单（上线前自查）

| 项 | 检查方式 |
|---|---|
| 🔴 `RMB01_SECRET_KEY` 已配 | `/healthz` 的 `secret_key_ephemeral` 为 false |
| 🔴 `RMB01_PASSWORD_SALT` 已配 | 检查环境变量 |
| 🔴 无明文密钥入库 | `grep -rE "sk-[A-Za-z0-9]{16,}" .` |
| 🔴 平台管理员密码已改 | 别用默认的 |
| 数据目录权限 | 非 root 可写，但不要 777（容器内用户即可） |
| 反向代理加 HTTPS | 应用本身不处理 TLS |
| 数据库不在公网 | SQLite 是文件，天然没有端口 |

## 九、快速诊断脚本

```bash
#!/bin/bash
echo "=== 健康检查 ==="
curl -s http://127.0.0.1:5001/healthz | python -m json.tool

echo "=== 容器用户 ==="
docker exec rmb01 id -un

echo "=== WAL 模式 ==="
docker exec rmb01 sqlite3 /app/data/rmb01.db "PRAGMA journal_mode;"

echo "=== busy_timeout ==="
docker exec rmb01 sqlite3 /app/data/rmb01.db "PRAGMA busy_timeout;"

echo "=== 账实相符 ==="
docker exec rmb01 sqlite3 /app/data/rmb01.db \
  "SELECT 'usage表', COUNT(*) FROM usage WHERE degraded=0;
   SELECT '订阅表', SUM(quota_used) FROM subscription;"

echo "=== 最近错误 ==="
docker logs rmb01 --tail 200 2>&1 | grep -iE "error|exception|failed" | tail -10
```
