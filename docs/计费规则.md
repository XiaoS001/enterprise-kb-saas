## 二、额度怎么算

### 2.1 一次问答扣多少？

**固定扣 1 次**，不看 token 数。原因：

- 客户不需要估算「我这个问题值多少钱」——按次最直观
- 按 token 计费要求客户理解模型差异（同样问题在不同模型上成本差几倍）
- 本项目阶段 4/5 的成本结构里，**模型调用不是主要成本**（见第六节）

### 2.2 什么情况**不扣**额度

| 情形 | 扣不扣 | 理由 |
|---|---|---|
| 正常问答（模型真的生成了答案） | ✅ 扣 1 | 消耗了模型额度 |
| **降级问答**（无 API key / 模型调用失败） | 🔴 **不扣** | 没调模型 = 没消耗额度 |
| 检索未命中（知识库里没有相关内容） | ❌ 不扣 | 没生成任何东西 |
| 参数错误（问题为空、超长） | ❌ 不扣 | 压根没开始 |

> 🔴 这条依赖 `agent._empty_result` 的 `degraded` 标记。
> 那个字段曾经硬编码为 `False`（降级了却不承认），会导致
> **降级问答被当正常问答扣费** —— 收了钱没提供服务。
> `tests/test_degraded_flag.py` 盯着这个字段不被改回去。

### 2.3 降级问答仍然记流水

不扣额度 ≠ 不记账。`usage` 表里会留一条 `degraded=True` 的记录，
运营可以在后台看到「有多少次是降级响应」——
**降级比例突然升高 = 该换 key 或该升配了**。

## 三、额度用完怎么办

### 3.1 接口行为

```http
POST /api/kbs/1/ask
→ 403 Forbidden
{
  "error": "本期额度已用完（100/100），可升级套餐",
  "code": "quota_exceeded",
  "plan": "free",
  "quota_used": 100,
  "quota_total": 100
}
```

🔴 **不是 500**。额度用完是正常的业务状态，不是系统故障。

### 3.2 前端提示文案

> 本期额度已用完（100/100）。升级到专业版可获得 10000 次/月，
> 或联系管理员调整。**在额度用完期间，你的知识库内容与检索功能仍可正常使用。**

### 3.3 恢复方式

1. 升级套餐（额度立即生效）
2. 或等下一个计费周期（`quota_used` 归零）
3. 或由运营在后台手动调高 `quota_total`

## 四、额度的技术保证

### 4.1 原子扣减

🔴 **绝不允许「先 SELECT 再 UPDATE」** —— 两个并发请求会同时读到
`quota_used=4`（总额 5），都判定「还有额度」，都写回 6 → **超扣**。

正确做法是单语句原子 UPDATE + 看 rowcount：

```sql
UPDATE subscription
   SET quota_used = quota_used + 1
 WHERE id = :sid
   AND quota_used < quota_total      -- ← 判定条件必须在 SQL 里
```

`rowcount = 1` → 扣成功；`rowcount = 0` → 额度不足。

用 `<` 而不是 `<=`：额度用尽的**那一次**就该被拒。

### 4.2 并发支撑

SQLite 的两个 PRAGMA：

| PRAGMA | 作用 |
|---|---|
| `journal_mode=WAL` | 读写不互斥（读者不阻塞写者，反之亦然） |
| `busy_timeout=5000` | 第二个请求**等待** 5 秒而不是立刻失败 |

🔴 **`busy_timeout` 是每连接生效的**。SQLAlchemy 的连接池会新建连接，
只在启动时设一次不够 —— 所以挂在 `connect` 事件上，让每条新连接都带上。

### 4.3 账实相符

**恒等式**：`Usage` 里 `degraded=False` 的条数 == `Subscription.quota_used`

这是计费系统最典型的 bug（两边对不上 = 要么多扣了、要么扣了没记账）。
`tests/test_billing.py::test_usage_count_equals_quota_used` 盯着它。

被额度拒绝的请求**不留流水**，否则流水数会多于 `quota_used`。

## 五、套餐变更

### 5.1 升级

随时可升，**额度立即生效**，已用量不变。

```python
change_plan(tenant_id, 'enterprise')
# quota_total: 100 → 100000
# quota_used:  90  → 90（不动）
```

### 5.2 🔴 降级的边界

**已用量超过新额度时，直接拒绝降级**，返回 `409 Conflict`：

```
当前套餐已用 5000 次，超过免费版的 100 次额度，降级前需先处理已用量
```

**为什么不自动截断已用量？**

假设 pro 用户已用 5000 次，降到 free（100 次）。如果自动把
`quota_used` 截断成 100，等于**凭空抹掉客户已消耗的 4900 次**——
不公平，且账单口径也乱了。

如果只改 `quota_total` 不动 `quota_used`，会出现
`quota_used(5000) > quota_total(100)`：
- `quota_remaining` 变成负数
- 之后每次扣减都被 WHERE 拒绝 → 租户**永久锁死**，升级回来也得先修数据

所以正确做法是**拒绝 + 让运营决定**（清零重开计费周期，或让客户用完）。

`tests/test_admin.py::test_downgrade_blocked_when_used_exceeds_new_quota` 盯着。

## 六、成本测算（真实数字，非估算）

### 6.1 单次问答的模型成本

以 DeepSeek-V4-Flash 为例：

| 项 | 量级 |
|---|---|
| 输入 | 检索证据约 500 token + 提示词约 300 = 800 token |
| 输出 | 答案约 300 token |
| 合计 | 约 1100 token |

**实际费用我没有真实账单数据，不编数字。**
按公开定价自行核算即可 —— 这一条应当由真实账单验证，
不是靠估算写进文档。

### 6.2 成本结构的定性判断

单次问答的成本**大头不在模型**：

| 成本项 | 说明 |
|---|---|
| 模型调用 | 有，但单次金额很小 |
| **向量检索** | 已默认关闭（fastembed + onnxruntime 约 82MB） |
| 存储 | 文档分段很小，日志留存 90 天量级可控 |
| 带宽 | 与问答次数线性相关 |

> 所以本项目**按次计费**而不是按 token 计费 ——
> 成本结构不支持精确到 token 的定价。

## 七、计量数据模型

`usage` 表（每次问答一行）：

| 字段 | 说明 |
|---|---|
| `tenant_id` | 🔴 租户隔离字段 |
| `kb_id` | 问的是哪个库 |
| `user_id` | 谁问的 |
| `question` | 问题（截断 500 字） |
| `tokens` | 🔴 **降级记 0**（没调模型就没 token） |
| `degraded` | 是否降级响应 |
| `created_at` | 时间 |
