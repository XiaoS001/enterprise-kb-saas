> ⚠️ **本文是设计推演，不是市场验证结论。**

---

## 一、目标客户

### 1.1 谁会买

| 客户类型 | 规模 | 痛点 | 付费意愿 |
|---|---|---|---|
| **中型企业 IT/运维团队** | 100–1000 人 | 运维手册、故障预案散在 Wiki/网盘/群聊，新人上手靠问人 | 中 |
| **企业内部知识管理** | 500–5000 人 | 制度文件、流程文档找不到最新版 | 中高 |
| **专业服务公司**（律所/咨询/会计） | 50–500 人 | 案例、模板、法规库需要精确检索且**必须能溯源** | 高 |
| **制造业工艺/质检** | 200–2000 人 | 作业指导书版本混乱 | 中 |

### 1.2 谁不会买

| 类型 | 原因 |
|---|---|
| 个人用户 | 免费工具（Notion AI、Obsidian + 插件）够用 |
| 超大企业（>1 万人） | 会自建，或用 Confluence + 云厂商 RAG 方案 |
| 已经在用 Dify/FastGPT 且满意的团队 | 迁移成本 > 收益 |
| 只需要「文档搜索」的 | 他们不需要问答，用 Elasticsearch 就行 |

### 1.3 真正的差异化卖点

**不是「AI 问答」** —— 这个能力满大街都是。真正的差异点是：

> 🔴 **答案必须标出「依据《XX文档》第 N 段」，且查不到就说查不到。**

为什么这值钱：

- 企业场景里，「听起来对但错了」比「不知道」危险得多
- 法务/合规/质检场景里，**不可溯源 = 不可用**
- 通用 AI 助手最大的问题就是「一本正经地胡说」，引用校验是目前唯一能约束它的工程手段

**毛利空间看起来很宽 —— 但这是假象**：

真正吃掉毛利的是**获客成本**和**服务成本**（客户成功、答疑、定制），
不是模型调用。

## 三、获客路径

### 3.1 分阶段（前 12 个月）

| 阶段 | 手段 | 目标 |
|---|---|---|
| 0–3 月 | 开源 + GitHub 引流 | 拿 star 和反馈，验证「引用校验」这个点有没有人认 |
| 3–6 月 | 技术博客 / 掘金 / V2EX 发「企业 RAG 怎么做引用溯源」 | 建立专业形象 |
| 6–12 月 | 找 3–5 家愿意试用的中小企业（免费换反馈） | 验证真实场景，积累案例 |
| 12 月+ | 案例驱动销售 | 才开始谈钱 |

### 3.2 获客成本（CAC）

**没有数据。** 不给推测数字。

可以确定的是：**To B 产品 CAC 通常远高于 To C**，
而且本产品的客户（IT 团队）决策周期长、需要试用和内部评估。

### 3.3 不适合的路径

| 路径 | 为什么不适合 |
|---|---|
| 投广告买量 | To B 长决策周期，广告转化率极低 |
| 面向个人做 freemium 冲量 | 个人用户不付费，撑不起成本 |
| 大规模销售团队 | 早期产品没有 PMF，招销售是烧钱 |

## 四、成本结构

### 4.1 单次问答的成本构成

| 项 | 量级 | 可信度 |
|---|---|---|
| 模型输入 | 约 800 token（证据 500 + 提示词 300） | 估算，基于本项目实际提示词长度 |
| 模型输出 | 约 300 token | 估算 |
| 向量检索 | **0**（默认关） | 确定 |
| 存储 | 每段几百字节 | 确定 |
| 计算 | 单次请求 CPU 极低 | 确定 |

### 4.2 🔴 我不给 token 单价

**原因：我没有真实账单数据。**

写一个看起来专业的「¥0.001/千 token」既可能偏高也可能偏低，
而这类数字会被当成事实引用。**没有数据就不编。**

要核算真实成本，正确做法是：

1. 用真实语料跑 1000 次问答
2. 从账单里读实际消耗
3. 除以次数

### 4.3 成本结构的定性判断

| 判断 | 依据 |
|---|---|
| **按次计费比按 token 更合理** | 客户不需要理解模型差异；本项目成本结构里模型不是主要项 |
| **免费版 100 次/日不会亏** | 100 次 × 30 天 = 3000 次/月，即便成本较高也在可承受范围 |
| **向量检索是成本放大器** | 嵌入模型 + 向量库 + 运维，都比 BM25 重。所以默认关 |

## 五、与 Dify 的差异

| 维度 | Dify | RMB01 |
|---|---|---|
| **定位** | 通用 LLM 应用开发平台（工作流/Agent/RAG） | **垂直**：企业知识库问答 |
| **多租户** | 有（Workspace） | 有（Tenant + 4 档角色 + 双层隔离） |
| **引用溯源** | 有引用，但**不强制**、不做「有证据却没引用」的拦截 | 🔴 **强制校验**：零引用 = 不合格；引用不存在的 doc = 拦截 |
| **检索** | 向量为主（依赖嵌入模型） | **BM25 为主**（零网络依赖），向量可选 |
| **部署** | Docker Compose（多组件） | **单容器**（一个 Flask 应用） |
| **代码量** | 数十万行 | 约 5000 行（可通读） |
| **商业模式** | 开源 + 云服务 | 开源 + SaaS（本项目未接入支付） |

### 5.1 不跟 Dify 比什么（诚实）

| 项 | 差距 |
|---|---|
| 功能广度 | Dify 有工作流编排、插件市场、多模型路由，本项目都没有 |
| 生态 | Dify 有社区、模板、教程，本项目没有 |
| 稳定性 | Dify 经过大量生产验证，本项目**只在测试环境跑过** |
| 前端 | Dify 有完整可视化编排界面，本项目只有一个极简页面 |

### 5.2 只在什么场景下选本项目

1. **需要可通读的代码**（安全审计、二次开发、教学）
2. **必须完全离线可控**（BM25 不联网）
3. **需要「引用必须可溯源」作为硬约束**
4. 团队小，不想维护十几个组件的技术栈

## 六、规模化后的关键挑战

按优先级：

| 挑战 | 为什么是问题 |
|---|---|
| 🔴 **真实模型效果未验证** | 所有测试都 mock，没跑过真实语料。这是最大风险 |
| 🔴 **SQLite → PostgreSQL** | 单机 + 单 worker 撑不住多客户 |
| **计费周期归零** | `quota_used` 只增不减，业务上不可用 |
| **无 Alembic** | 改表结构要手工迁移，客户数据无法平滑升级 |
| **无 `/metrics`** | 出问题看不见 |
| **无支付接入** | 收不了钱 |
| **前端太简陋** | 客户没法自助使用 |
